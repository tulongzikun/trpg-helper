# 车卡 → 战斗导入协议：CharacterSnapshot v1

> 版本：v1.0（2026-11-10）
> 依赖：《车卡系统_独立模块设计_v1.0.md》与《DnD_5E_单机多人战斗系统_完整设计文档_v2.0.md》
> 目标：定义唯一、可测试、与 UI 无关的角色发布/导入边界。**禁止直接把车卡草稿当作战斗 Actor。**

## 1. 接口设计原则

1. **单向数据流**：Builder 发布不可变 CharacterSnapshot → BattleImportAdapter → 战斗 BattleActor。禁止 Battle 直接写 builder 的表。
2. **Schema 与 RulePack 双版本**：schemaVersion 用于处理文件格式迁移；edition/rulePackHash 用于规则语义。不能仅靠同名职业/法术判断兼容。
3. **来源完整**：所有获得的能力有稳定 ID 和来源规则，不能只提供用于展示的中文名称或伪造战斗效果。
4. **快照 vs 运行时**：快照可以包含发布时的最大生命和可用资源上限；不得包含正在战斗的当前 HP、当前先攻、死亡豁免、专注或正在场上的召唤物。
5. **导入原子性**：先全面预检，用户确认，再一次性导入并写日志；任一错误不得留下半个 Actor。
6. **无循环依赖**：contract 不导入 builder/combat 包；adapter 可以依赖 contract 和 rules，但 builder 不依赖 combat。
7. **可重演性**：导入记录快照 SHA-256、角色 revision、规则哈希和初始化参数。

## 2. CharacterSnapshot v1 结构

~~~typescript
type Ability = "str" | "dex" | "con" | "int" | "wis" | "cha";

interface CharacterSnapshotV1 {
  schemaVersion: "character-snapshot/v1";
  characterId: string;            // 角色库内部稳定 ID
  revision: number;               // 每次发布递增；不是角色等级
  publishedAt: string;            // ISO-8601
  rule: {
    edition: "dnd5e-2014" | "dnd5e-2024";
    ruleSetId: string;            // 如 srd-5.2.1
    rulePackVersion: string;
    rulePackHash: string;         // 规则包内容摘要
    appliedHouseRuleIds: string[];
  };
  identity: { name: string; description?: string };
  build: {
    classLevels: Array<{
      classId: string;
      level: number;
      subclassId?: string;
    }>;
    backgroundId: string;
    speciesId: string;
    abilities: Record<Ability, number>; // 最终属性，不含战斗临时增减
    featIds: string[];
    chosenOptions: Record<string, string[]>;
    proficiencies: {
      saves: Ability[];
      skills: string[];
      weapons: string[];
      armor: string[];
      tools: string[];
    };
    languages: string[];
  };
  features: Array<{
    abilityId: string;
    sourceRuleId: string;
    sourceType: "class" | "subclass" | "species" | "background" | "feat" | "equipment" | "other";
    grantsAtLevel?: number;
    parameters?: Record<string, string | number | boolean>;
  }>;
  equipment: Array<{
    itemId: string;
    quantity: number;
    equipped: boolean;
    attuned?: boolean;
    baseItemId?: string;         // 如魔法武器模板引用基础武器
  }>;
  spellcasting: Array<{
    sourceId: string;            // 职业/特性授予的施法来源
    ability: Ability;
    knownSpellIds: string[];
    preparedSpellIds: string[];
  }>;
  derived: {
    totalLevel: number;
    maxHp: number;
    baseAc: number;              // 当前装备/特性静态导出值，战斗必须可重算
    speedFt: number;
    proficiencyBonus: number;
    resourceMaxima: Record<string, number>;
  };
  provenance: {
    origin: "internal-builder" | "manual" | "external-adapter";
    sourceName?: string;
    sourceFingerprint?: string;
  };
}

interface PublishedSnapshotEnvelope {
  document: CharacterSnapshotV1;
  contentSha256: string;         // canonical JSON(document) 的 SHA-256
}
~~~

注：这个协议特意不把角色快照与战斗 Actor 做同构设计。角色卡保留构筑事实和来源；Battle Actor 添加 HP、临时 HP、行动预算、状态、位置、召唤关联和先攻。

定义中的具体 TypeScript 类型、必填字段需要由 packages/contracts 进一步固化为 Zod/JSON Schema，schemaVersion 是之后迁移的分发单位。

## 3. 导入命令与响应

~~~typescript
interface ImportCharacterCommand {
  battleId: string;
  source: PublishedSnapshotEnvelope;
  sideId: string;
  spawnPosition?: { x: number; y: number; zFt?: number };
  initialState: {
    hp: "FULL" | { value: number };   // 默认 FULL
    tempHp?: number;                 // 默认 0
    resources: "FULL" | Record<string, number>;
  };
  existingCharacterPolicy: "ALLOW_MULTIPLE" | "REJECT_DUPLICATE";
}

interface ImportValidation {
  ok: boolean;
  errors: Array<{ code: string; path: string; message: string }>;
  warnings: Array<{ code: string; path: string; message: string }>;
  preview?: {
    name: string;
    level: number;
    ruleSetId: string;
    hpMax: number;
    ac: number;
    features: string[];
    spellSlotMaxima: Record<string, number>;
  };
}

interface ImportedCharacterRef {
  actorId: string;                 // 新 UUID，不等于 characterId
  characterId: string;
  characterRevision: number;
  snapshotHash: string;
  rulePackHash: string;
}
~~~

导入器接口：

~~~typescript
interface BattleCharacterImporter {
  validate(snapshot: PublishedSnapshotEnvelope, battle: BattleState): ImportValidation;
  preview(cmd: ImportCharacterCommand, battle: BattleState): ImportValidation;
  commit(cmd: ImportCharacterCommand, battle: BattleState): {
    nextState: BattleState;
    actorId: string;
    events: BattleEvent[];
  };
}
~~~

## 4. 导入完整流程

~~~text
角色库选择“发布快照”/战斗页面点击“导入 PC”
       ↓
读取 CharacterSnapshot v1 + contentSha256
       ↓
schemaVersion 检查 → canonical hash 校验
       ↓
RulePack edition / id / hash 兼容检查
       ↓
Feature、spell、equipment 引用解析 + 自动结算支持能力检查
       ↓
重算 derived 数据并校对 HP、AC、熟练、资源、等级
       ↓
预览并选择阵营、位置、初始生命和资源
       ↓
一次性创建 BattleActor（新 UUID + 来源引用）
       ↓
生成 CharacterImported 事件、持久化 BattleState
       ↓
显示战斗可用行动，包含 Extra Attack/Action Surge/Second Wind 等
~~~

校验顺序：

| 检查 | 行为 |
|---|---|
| draft/未发布 | ERROR：不允许导入 |
| schemaVersion 未知 | ERROR：必须先使用显式迁移器 |
| SHA 不匹配 | ERROR：拒绝损坏文件 |
| ruleSetId/edition 不匹配 | ERROR：不能跨 2014/2024 静默转换 |
| 缺失 RulePack 内容/hash 不匹配 | ERROR：提示安装正确规则包/版本 |
| 任一能力缺少规则定义 | ERROR 或由明确房规禁用该能力，并要求用户确认；不能假装可以自动结算 |
| 缺失法术、装备定义 | ERROR：标出具体 ruleId |
| derived 与重算不同 | ERROR：需要在车卡页重新发布；不信任导入静态值 |
| characterId 重复 | 遵循 existingCharacterPolicy，不应复用 actorId |
| 负数或超限的初始 HP/资源 | ERROR；禁止绕过配置流程 |
| 快照包含动态 combat 字段 | schema 不识别或显式忽略，不据此改变进行中战斗 |

如果是无地图模式，位置可以留空；需交由战斗的声明式目标模式限制距离判断，不能伪称已验证几何与视线。

## 5. 战斗 Actor 的来源与状态分离

~~~typescript
interface SourceCharacterRef {
  characterId: string;
  revision: number;
  contentSha256: string;
  ruleSetId: string;
  rulePackHash: string;
}

interface ImportedBattleActor {
  id: string;                    // 与 CharacterSnapshot characterId 不相同
  kind: "PC";
  sourceCharacter: SourceCharacterRef;
  sideId: string;
  name: string;
  // 静态/可重算属性从快照和规则构造
  stats: {
    abilities: Record<Ability, number>;
    ac: number;
    maxHp: number;
    speedFt: number;
  };
  abilities: string[];           // 战斗规则中可解析的能力 ID
  // 完全独立的运行时状态
  hp: number;
  tempHp: number;
  resources: Record<string, { remaining: number; maximum: number }>;
  conditions: string[];
  concentrationEffectId?: string;
  position?: { x: number; y: number; zFt?: number };
  // turnBudget / death / control / initiative 由战斗引擎创建
}
~~~

实际项目可沿用 v2.0 战斗文档的 Actor 数据结构，并增加 sourceCharacter 引用；上面是**映射视图**而不是替代整份 Actor 类型定义。所有运行时变量由战斗引擎创建并拥有。

## 6. 职业与召唤映射验收案例

**战士 5 级**

- Character Builder 导出职业等级、Extra Attack、Action Surge、Second Wind 对应 abilityId 和来源。
- Battle ImportAdapter 解析规则包，产生 Attack 动作（一次攻击动作含两次攻击机会）、Action Surge 资源以及 Second Wind 附赠动作技能。
- 玩家先 Attack（两击）再 Action Surge + Attack（两击）时，最多仍可用一次 Bonus Action；回气扣职业资源和唯一附赠动作。角色快照本身无需记录任何 turnBudget。

**召唤型施法者**

- 发布快照导出已准备法术/召唤特性 ID 和施法能力/法术资源上限。
- 战斗中成功施法后由 SummonEngine 生成独立生物 BattleActor，使用其自身 stat block、ownerId、sourceEffectId、initiativePolicy 和 commandPolicy。
- 召唤物被 AoE 命中、死亡或主人专注失败而消失，只影响当前 BattleState；Builder 的角色卡里不产生永久召唤物。
- 如果某个规则明确允许长期伴随的伙伴模板，可以在快照里导出 companion specification，但战斗依然生成新的 Runtime Actor。

**施法者 AoE**

- 已准备的 Fireball 由 Snapshot 获得资格。
- Battle AoE Engine 结合目标几何或无地图申报模式找到所有受影响单位（包括友军和召唤物），分别结算豁免和抗性。
- 扣 HP 等不回写车卡。

## 7. 升级、重发布与历史战斗

情境：同一角色发布 revision 3 → 导入战斗 B1；后来车卡升级并发布 revision 4 → 导入战斗 B2。

- B1 一直使用 revision 3 的构筑与 RulePack 哈希；B2 使用 revision 4。
- B1 中的伤害和资源变化不能流入 revision 3 或 4。
- B1 即使重新打开/回放，也不自动读取角色库里的“最新版本”。
- 如果未来开放“战斗中热更新”，必须显式暂停对局、运行转换检查、存储新分支日志；默认禁止。

## 8. 外部 TRPGCard / 文件导入策略

~~~text
TRPGCard 合法导出 / 手工录入 / 其他合法格式
   └─ SourceAdapter (各数据源独立)
         └─ ExternalCharacterDraft + warnings
               └─ builder 选择/修复缺失字段
                     └─ CharacterDraft
                           └─ validate + publish
                                 └─ CharacterSnapshot v1
                                       └─ BattleImportAdapter
~~~

不能绕过 builder 的合法性验证，把缺失的法术、特性或职业参数推断成“已知”并加入战斗。当前没有验证 TRPGCard 稳定的导出 API，不应把自动抓取作为依赖。

## 9. 原子性、数据安全和迁移

- 本地 storage：character_revisions 保持不可变；battle_actors 和 battle_snapshots 独立存储。
- 同一次导入使用同一原子事务更新 Actor、战斗 revision 和 CharacterImported 事件；出错一律回滚。
- 使用 schema migration（v1 → v2）而不是事后偷偷改写旧历史文件。
- 尽管单机运行，也应进行输入校验、大小限制、恶意 JSON 字段过滤和 HTML 内容转义；来源描述和备注不是可执行脚本。
- 导出时为用户提供 JSON 文件；导入日志保留 actorId、snapshot hash、rule hash、错误/警告、时间。
- 使用稳定键顺序序列化计算 hash；随机 UUID 的 actorId 独立生成。

## 10. 验收测试清单

1. 有效 1 级 PC 成功导入；Battle Actor 有独立 ID，来源引用完整。
2. 同一发布修订版导入两场战斗，分别受到伤害，互不污染。
3. 角色库修改草稿，进行中战斗属性不改变。
4. 角色升级发布后，旧战斗仍为旧等级、旧资源、旧特性。
5. 未完成草稿不允许导入。
6. 篡改快照一项六维属性导致 SHA 不符，拒绝导入。
7. 使用错误 2014/2024 规则包，拒绝导入。
8. 修改 derived.attackBonus 等静态数据无法绕开重算器。
9. 战士 Extra Attack 与 Action Surge 都可用，附赠动作次数始终不超过 1。
10. 施法者实际施法消耗法术位但库中角色卡不变。
11. 召唤物创建/消失、AoE 误伤与专注失败不影响快照。
12. 手工 JSON 字段缺失时列出可定位的失败路径。
13. 导入至不允许的阵营或超 HP 失败时不留下半个 Actor。
14. 允许重复角色导入时，来源相同但 actorId、HP 和资源各自独立。
15. 从旧 schema 迁移前后保留来源审计；未知 schema 版本不能静默导入。

## 11. 总结

**车卡系统负责“角色是什么、学会了什么、理论上拥有哪些资源”。**
**战斗系统负责“当前如何行动、对谁生效、还剩多少资源、战场上发生了什么”。**

两者只经由版本化 CharacterSnapshot 的发布/导入协议交换数据，避免双向耦合和历史战斗漂移。
