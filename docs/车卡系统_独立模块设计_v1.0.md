# D&D 5E 车卡系统——独立模块技术设计

> 版本：v1.0（2026-11-10）
> 适用仓库：tulongzikun/trpg-helper
> 首版规则：D&D 2024 / SRD 5.2.1；2014 / SRD 5.1 用独立规则包接入
> 设计定位：**完全独立的角色创建、维护和升级模块**；无需启动战斗、不依赖战斗状态；通过版本化角色快照导入战斗
> 状态：产品及技术设计，不代表功能已编码实现

## 1. 目标和非目标

### 1.1 用户故事

- 从零创建 PC：选规则版本、角色名称、职业、背景、物种、属性、技能/工具熟练、装备、专长、法术、人物资料。
- 每一步自动给出合法候选项、说明来源和前置条件；支持草稿保存、退出后恢复、撤销与修改上游选择。
- 随时显示角色卡预览：等级、六维、调整值、熟练加值、HP、AC、先攻、速度、攻击、熟练、法术数据、职业特性、资源。
- 支持角色升级、职业分级和选择历史，未来支持多职业、重训、房规扩展。
- 发布可用的角色卡快照；在战斗页选择已发布角色，导入任意多个角色到不同阵营。
- 战斗中出现的 HP、法术位、专注、召唤物等变化**不回写**车卡；结束战斗允许用户显式选择把特定成长/装备变动作为新草稿变更提案。
- 支持外部合法 JSON/手动录入；TRPGCard 无可证实的公开导出 API 时不能把其直接集成视为依赖。

### 1.2 非目标

- 本模块不管理先攻、回合、命中、伤害、死亡豁免、移动和 AoE 受击对象。
- 本模块不生成当前战斗中的召唤实体，只导出召唤能力及其规则来源。
- 首版不包含联网账号、多人协同修改、购买受版权保护规则书、未经授权的专有内容导入。
- 不把“角色显示在表格中”误认为已合法完成车卡；未解决必填选择不得发布。

## 2. 模块边界和依赖方向

~~~text
┌────────────── 车卡应用 Character Builder ──────────────┐
│ Character Wizard / Library / Sheet / Advancement       │
│       ↓                                                │
│ Draft Store → Choice & Constraint Engine               │
│       ↓                  ↓                             │
│ Rule Resolver ←  Rules Catalog (immutable RulePack)    │
│       ↓                                                │
│ Derived Stat Calculator + Validator                    │
│       ↓                                                │
│ Publish CharacterSnapshot v1                           │
└──────────────────────────┬─────────────────────────────┘
                           │ JSON / stable schema + hash
                  Battle Import Adapter
                           │
┌──────────────────────────▼─────────────────────────────┐
│ 战斗引擎 Battle                                        │
│ normalize + validate + clone → BattleActor             │
│ 独立运行时 HP/资源/状态/位置/回合/召唤物                  │
└────────────────────────────────────────────────────────┘
~~~

依赖约束：

1. builder 可以依赖 shared-rules 和 shared-contracts；**不得依赖 combat-engine**。
2. combat-engine 可以依赖 shared-rules、shared-contracts 和独立的 import-adapter；**不得调用 builder 的草稿、存档或 UI**。
3. 两边共同引用同一个不可变规则包（ruleSetId + rulePackHash），但各自维护独立状态。
4. 快照发布和战斗导入属于不同事务；一次发布不会自动改变现有战斗。

建议仓库目录：

~~~text
apps/web/src/features/character-builder/
  pages/                  # 角色库、向导、角色卡、升级
  components/
  application/            # draft / validate / publish commands
  domain/                 # entities / choice / calculation / history
  persistence/            # IndexedDB adapters
apps/web/src/features/battle/  # 原战斗 UI，互不依赖
packages/rules/            # SRD 规则 JSON、schema、版本适配
packages/contracts/        # 发布和导入的公开 DTO schema
packages/character-core/   # 纯函数：车卡检查与衍生数值
packages/combat-core/      # 纯函数：战斗事件解析
packages/battle-import/    # Snapshot → BattleActor
~~~

## 3. 车卡页面与用户流程

主导航：**角色库 / 新建角色 / 战斗 / 规则包**。

角色库以卡片形式展示名称、职业组合、等级、规则版本、有效性、草稿版本、上次发布时间。提供“编辑”“复制”“升级”“发布”“导出 JSON”“导入战斗”。

### 3.1 新建向导（2024 版默认顺序）

1. **规则与基础信息**：SRD 5.2.1、允许的来源和房规、角色名称、起始等级；锁定版本。
2. **职业**：职业、初始等级、初始熟练、生命骰、职业特性；逐项完成技能与职业选项。
3. **起源**：背景、物种、语言、起源专长、种族特性；背景关联的属性提升与技能。
4. **六维属性**：标准数组、27 点购点、4d6 去最低或受约束的手动值；记录生成方法、原始骰子、分配、背景加成来源。
5. **职业成长选择**：等级对应的分支、战斗风格、专长/属性提升、职业资源、法术选择与准备；分支只在规则要求的等级开启。
6. **装备与金币**：职业和背景起始装备选择、购买/替换、武器、防具、盾牌、物品实例以及必要的同调检查。
7. **人物资料**：姓名、阵营（若启用）、外貌、背景故事、备注；不影响规则合法性。
8. **核对并发布**：未完成选择清单、规则来源、衍生数值解释、数据完整性及“导入战斗”入口。

备注：实际依赖校验是图结构，**UI 的步骤顺序不等于规则的计算顺序**。允许任意返回步骤修改，系统只使受影响的后续选择失效。

### 3.2 属性面板与预览

同屏展示基础属性、背景/特性加成、最终值和计算来源；HP、AC、武器命中与伤害、豁免、技能、法术攻击/DC、已准备法术和资源。每一项有“来源解释”（如战士职业、背景、装备、专长），不只是最终数字。

### 3.3 草稿、保存与发布

- 编辑草稿：自动保存至 IndexedDB，可有未完成选择，不可用于战斗。
- 验证：产出问题清单，区分 ERROR（禁止发布）、WARNING（允许发布需确认）、INFO。
- 发布：严格验证，产生**不可变的 CharacterSnapshot 修订版**并记录规则包 hash；每次发布递增 revision。
- 战斗：仅允许选择“已发布且当前导入器兼容”的快照；历史版本可继续导入和回放。
- 升级：从最近发布快照派生新草稿并产生升级记录；旧快照不修改。

## 4. 领域模型（TypeScript 建议）

~~~typescript
type Ability = "str" | "dex" | "con" | "int" | "wis" | "cha";
type RuleEdition = "dnd5e-2014" | "dnd5e-2024";
type BuildStatus = "draft" | "ready" | "published";

interface RuleBinding {
  edition: RuleEdition;
  ruleSetId: string;      // srd-5.2.1
  rulePackVersion: string;
  rulePackHash: string;   // 规则包内容稳定哈希
  allowedSources: string[];
  houseRuleIds: string[];
}

interface CharacterDraft {
  id: string;
  baseRevision?: number;
  status: BuildStatus;
  rule: RuleBinding;
  identity: { name: string; description?: string; portraitRef?: string };
  classLevels: Array<{ classId: string; level: number; subclassId?: string }>;
  origin: { backgroundId?: string; speciesId?: string; languageIds: string[] };
  abilityGeneration: {
    method: "standard-array" | "point-buy" | "rolled" | "manual";
    baseScores: Record<Ability, number>;
    adjustments: Array<{ sourceId: string; ability: Ability; amount: number }>;
    rollHistory?: number[][];
  };
  choices: Record<string, string[]>;  // choiceId → selected optionIds
  inventory: Array<{ itemId: string; quantity: number; equipped?: boolean; attuned?: boolean }>;
  knownSpellIds: string[];
  preparedSpellIds: string[];
  notes?: string;
  updatedAt: string;
}

interface ValidationIssue {
  severity: "ERROR" | "WARNING" | "INFO";
  path: string;
  code: string;
  message: string;
  sourceRuleId?: string;
}
~~~

重要：CharacterDraft 表示**选择事实**，不是仅存一个扁平角色最终数值。重算来源必须可追踪，避免更换规则包或背景后遗留陈旧的能力值。

## 5. 规则数据和选择引擎

规则对象使用稳定 ID、来源、版本、前置条件和效果描述，不允许仅依赖中文展示名定位。

~~~typescript
interface RuleEntity {
  id: string;
  source: { packId: string; ruleId: string };
  prerequisites?: Condition[];
  grants?: Grant[];
  choices?: ChoiceSlot[];
}
interface ChoiceSlot {
  id: string;
  count: number;
  options: string[];
  prerequisites?: Condition[];
  exclusivityGroup?: string;
}
~~~

规则引擎需要解决：

- 等级、职业、子职业、背景、物种、能力值、已有熟练、专长、法术等级等前置条件；
- 互斥选择、数量上限、特殊替换规则、重复熟练的版本差异、装备同调限制；
- 依赖树失效传播：修改职业后重新检验技能、武器熟练、职业特性、法术、HP；不合法部分变成 unresolved choice，而非静默保留；
- 可用法术与准备数量依具体职业规则，不统一写死；升级/多职业应由 RulePack policy 判定；
- 特性来源必须记录 level、classId、ruleId、选择来源，以便后续战斗引擎判断是否有 Extra Attack、Action Surge 等能力。

公开的最小接口：

~~~typescript
function getAvailableChoices(draft: CharacterDraft, choiceId: string, rules: RulePack): ChoiceOption[];
function applyChoice(draft: CharacterDraft, choiceId: string, selections: string[], rules: RulePack): CharacterDraft;
function reconcileDraft(draft: CharacterDraft, rules: RulePack): { draft: CharacterDraft; invalidated: string[] };
function validateDraft(draft: CharacterDraft, rules: RulePack): ValidationIssue[];
function deriveSheet(draft: CharacterDraft, rules: RulePack): DerivedCharacterSheet;
~~~

上述函数不应该访问战斗存档，且尽量纯函数化，以支持单元测试、回放、版本迁移。

## 6. 属性生成、校验与计算

2024 SRD 基线提供标准数组、27 点购点、4d6 去最低等方法。标准数组为 15、14、13、12、10、8；购点在规则允许的 8–15 分区间按成本表验证；背景的属性加成须满足所选背景允许的属性和分配限制。2014 版使用对应自身版本的来源和分配规则，不能沿用 2024 背景策略。

~~~typescript
type DerivedCharacterSheet = {
  totalLevel: number;
  abilities: Record<Ability, number>;
  modifiers: Record<Ability, number>;
  proficiencyBonus: number;
  maxHitPoints: number;
  armorClass: number;
  speedFeet: number;
  initiativeBonus: number;
  attacks: Array<{
    sourceRuleId: string;
    attackBonus: number;
    damageFormula: string;
    damageType: string;
    reachOrRange: string;
  }>;
  resources: Record<string, { max: number; recharge: "short-rest" | "long-rest" | "other" }>;
  featureIds: string[];
  spellcasting?: {
    spellAttackBonus: number;
    spellSaveDc: number;
    slotsByLevel: Record<string, number>;
    preparedSpellIds: string[];
  };
};
~~~

属性调整值 floor((score - 10)/2)，熟练加值随总角色等级变化；HP 升级点数、AC 优先级、专长与装备叠加、临时数值、豁免和各种法术资源均需由版本化策略计算。显示数值可以缓存，但**选择数据与规则来源是权威数据**。

HP 最大值在车卡发布时计算；战斗中当前 HP 不属于发布快照。人物升级后默认生成新发布版本，不会影响正在进行的战斗。

## 7. 职业特性与召唤能力的接口

车卡系统负责获得和解析职业特性，不负责执行它们：

- 2024 战士 5 级可获得 Extra Attack，战斗中一次 Attack action 允许多个 attack segments；
- Action Surge 提供额外普通动作，不增加附赠动作；
- Second Wind 需要附赠动作及职业资源，战斗中严格每回合至多一次附赠动作；
- 野兽伙伴、魔宠、召唤法术：车卡发布的是 ability/companion/summon specification（特性、施法消耗、可创建的实体模板 ID、指挥规则）；真正召唤单位在战斗中生成，并采用其自身的回合/指挥约束；
- 法术准备、法术位最大值、施法能力来源由车卡确定；当前法术位、专注和效果存续由战斗维护。

对于不在当前 RulePack 中的第三方特性，发布时可保留描述，但自动对战必须提示未支持并阻止无定义能力自动结算，或走明确的人工裁定机制。

## 8. 数据持久化与版本策略

首版无需后端，建议 React + TypeScript、独立的 character-core、IndexedDB（可用 Dexie 封装）、Zod/JSON Schema 校验。

对象存储：

| 表/集合 | 主要字段 | 用途 |
|---|---|---|
| character_drafts | id, baseRevision, document, updatedAt | 可编辑工作副本 |
| character_revisions | characterId, revision, snapshot, sha256, publishedAt | 不可变发布记录 |
| character_choices_audit | characterId, timestamp, action, before/after | 变更历史与回滚 |
| rule_packs | ruleSetId, contentHash, version | 冻结可重算规则 |
| external_imports | source, sourceFileHash, mappingWarnings | 第三方导入来源审计 |

发布后保留旧修订版；使用 canonical JSON（稳定 key 顺序）计算内容 hash。规则包升级时不能悄悄重算并覆盖历史角色，应提供“迁移为新草稿”流程及变更报告。

## 9. 与战斗的关系：仅通过公开快照契约

Character Builder 的输出是 CharacterSnapshot v1；Battle Import Adapter 做兼容性检测、完整性和来源验证，再**克隆**成 BattleActor。具体 schema 见《车卡导入战斗_数据契约_v1.0.md》。

必须成立的边界约束：

1. 战斗不可从未发布的草稿导入。
2. 导入角色后，战斗保留来源 characterId + revision + snapshotHash，原角色库不会被改变。
3. 同一角色可导入多个独立战斗，战斗各自拥有独立 HP、资源、效果和位置。
4. 升级/重新发布只影响未来导入；正在运行的战斗不会实时改变。
5. 源规则包不可用或 hash 不匹配时要求明确重新映射/拒绝自动结算，不能静默按另一规则版本运行。
6. 召唤生物通常不作为独立 PC 草稿创建；战斗依据召唤能力和规则模板生成。
7. P0 从角色库“导入战斗”可以创建新战斗或将角色加入进行中的战斗；操作时显示初始化 HP、阵营、位置、战斗资源和冲突警告，且独立提交。

~~~text

/characters/:id/edit              编辑草稿（向导）
/characters/:id/sheet             查看已发布角色卡
/characters/:id/history           修订记录
/characters/:id/level-up          升级向导
/characters/:id/export            导出快照
~~~

路由是 UI 层的建议，character-core 本身应可无 UI 运行，未来便于桌面端、CLI、测试或外部系统复用。

## 11. 验收标准与测试矩阵

**P0（必须通过）**

1. 新建 2024 1 级战士，能选择职业、背景、物种、分配属性和技能并发布。
2. 标准数组六项只能各用一次；购点预算 27 不能超支；掷骰流程保留记录。
3. 背景属性加成合法性必须校验，不允许向不允许的属性自由加点。
4. 返回修改职业时，职业特定技能/法术/装备和特性失效处理正确；合法选择尽量保留。
5. 角色没有完成必填技能或特性选择时，草稿可存、发布被阻止，并解释缺少什么。
6. 装备切换能影响 AC 和武器攻击资料；未满足熟练要求时能够解释影响。
7. 1→5 级战士后获得正确额外攻击能力，Action Surge 与 Second Wind 分开输出。
8. 创建一个有施法能力的角色，按规则输出法术 DC、法术攻击加值、法术位上限和已准备法术。
9. 角色库重新进入后草稿和所有选择完整保留，无需连接战斗模块。
10. 已发布快照不可被就地修改，修改后产生新 revision 和 hash。
11. 把战士和施法者分别导入同一战斗，HP、法术位和职业资源按导入策略初始化。
12. 战斗结束，角色库中发布角色的 HP、法术位与装备保持不变。
13. 同一角色导入两场战斗，任何战斗状态变化均不串线。
14. 角色升级至新 revision，旧战斗仍保持旧等级和旧特性。
15. 已发布角色导出/导入 JSON 后，规范化数据与计算结果一致。
16. RulePack 版本不匹配、缺失规则 ID、无效选择均被导入预检查拦截。
17. 召唤法术/伙伴只导出规范，战斗里创建的召唤物不污染角色库。
18. 外部角色源字段不完整时有可定位错误，不凭空补齐职业特性或自动施法效果。

**P1**：多职业、2014 适配、换装/重训、增量升级迁移、独立房规包、导入第三方 JSON 格式、可选的人工裁定与管理器。
