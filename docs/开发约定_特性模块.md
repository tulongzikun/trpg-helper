# 非战斗特性实现与核对约定（执行期）

> 适用：`docs/2024角色非战斗特性核对清单.md` 的执行阶段。
> 目的：让多个 agent 并行工作而不互相破坏，产出可验证、可追溯的结果。
> 规则基线：D&D 2024 / SRD 5.2.1；只评价角色卡，不要求自动执行战斗，也不替代主持人裁定。

## 1. 完成定义（Definition of Done）

单个核对清单条目完成 = 同时满足：

1. 已读规则文本（本地缓存，见 §2），确认等级、有效条件、资源与恢复方式；
2. 判断该条在角色卡上的归属：**角色卡数值/选择/记录**、**仅提示文本**、还是**仅战斗结算（不适用）**；
3. 属于角色卡的缺口已实现（模块 + 界面 + 测试），或明确说明为何只能提示；
4. 核对清单该行改成最终状态，并按 §6 格式记录：来源、等级、条件、界面、派生效果、资源恢复、测试证据；
5. 该组测试通过，`tsc --noEmit` 无新增错误。

禁止把「记录使用次数」当作「实现效果」；未核实就写 `待核查`，不要猜。

## 2. 规则来源与本地缓存

- 规则页原始 URL 已写在核对清单各小节的「规则来源」行。
- 本地已缓存全部 12 职业 + 48 子职业页面文本（**仅用于本地核对，属第三方文本，不得提交进仓库**）：
  - `.cache/rules/text/<职业>.txt`（如 `野蛮人.txt`）
  - `.cache/rules/text/<职业>_<slug>.txt`（如 `野蛮人_berserker.txt`）

- `.cache/` 已在 `.gitignore` 中；**不要把规则原文复制进 `docs/`、`src/` 或提交信息**。需要引用时最多一句短引文。

## 3. 单项分类与状态词

对每个条目先做分类，再决定是否写代码：

| 分类 | 判据 | 角色卡处理 | 状态写法 |
|---|---|---|---|
| 角色卡数值/选择/记录 | 影响属性、AC、速度、HP、熟练、语言、工具、法术选择、资源次数、派生值 | 必须实现（模块+界面+测试） | `已接入：…` 或 `部分：…` |
| 仅提示 | 规则存在但只能靠人记录/裁定（如持续时间内的人工判断） | 界面给出说明与手动记录位 | `部分：…需手动管理` |
| 仅战斗结算 | 只在战斗轮内生效：攻击/伤害/豁免/HP/先攻/动作经济/条件 | 不实现自动化，不写入战斗系统 | `不适用（战斗）：仅战斗轮内生效，本清单不要求自动化` |
| 角色卡无效果 | 纯背景描述、或已由现有通用机制覆盖 | 说明覆盖位置 | `已接入：由 <模块/界面> 覆盖` |

注意：
- 一个特性常是混合的（如「狂暴」= 战斗效果 + 次数资源 + 提示）。拆开写：能记录的次数/恢复必须接入；战斗加值标记为战斗。
- 现有状态词只有 `已接入 / 部分 / 待核查`，新增 `不适用（战斗）` 与 `待分类` 需在清单「状态说明」补一句（由 Lead 统一改）。
- 不要把 `待核查` 留在已分工完成的小节里。

## 4. 代码结构模板

每个特性按现有模式拆三处，**全部新建文件、不要改别人的文件**：

1. 领域模块 `apps/web/src/<feature>.ts`：纯函数，输入 `CharacterDraft`，输出派生值/新 draft/校验错误。禁止 React、禁止 DOM、禁止网络。
2. 视图 `apps/web/src/<Feature>Views.tsx`：`<Feature>Editor({draft,onChange})` 与 `<Feature>Sheet({draft})`；不适用时返回 `null`。
3. 测试 `tests/<feature>.test.cjs`：`require('../apps/web/src/<feature>.ts')` 直接用 Node 24 类型剥离加载，断言用中文消息。

参考实现（照抄结构，不要照抄内容）：
- 小模块：`apps/web/src/giantForm.ts` + `apps/web/src/GiantFormViews.tsx` + `tests/speciesResources.test.cjs`
- 资源型：`apps/web/src/classResources.ts` + `apps/web/src/ClassResourceViews.tsx`
- 较长恢复逻辑：`apps/web/src/specialRecovery.ts` + `apps/web/src/SpecialRecoveryViews.tsx` + `tests/specialRecovery.test.cjs`

约定：
- 用 `draft.details?.fighterCalculator?.<字段>` 读状态；`onChange({...draft, details:{...draft.details, fighterCalculator:{...fc, 字段}}})` 写状态（参考 `giantForm.ts`）。
- 视图用现有样式类：`character-section` / `section-label` / `character-help` / `sheet-text` / `button-secondary`；输入控件加 `aria-label`。
- 面向用户的中文文案，简洁说明「能自动算什么、什么要人工处理」。
- 不加新依赖；不引入战斗模拟；不动 `battle.ts` / `BattleViews.tsx`。
- 代码风格偏紧凑（项目现状一行多语句），但保持可读；类型显式。

## 6. 核对清单行格式

每行是单行 Markdown，保持原有 `- [ ] 等级 · 名称 — 状态：说明` 结构：

```
- [ ] 5 级 · 快速移动 — 已接入：未着装重甲时速度 +10 尺；界面：DerivedStats「速度」；测试：tests/barbarianFeatures.test.cjs；资源：无；来源：PHB2024 野蛮人页。
- [ ] 2 级 · 鲁莽攻击 — 不适用（战斗）：仅影响攻击检定与受击，角色卡无数值变化。
- [ ] 1 级 · 狂暴 — 部分：次数与恢复已接入（ClassResource「狂暴」）；伤害加值/抗性/持续需战斗轮内处理；测试：tests/classResources.test.cjs。
- [ ] 3 级 · 原初学识 — 已接入：额外职业技能 + 狂暴期间力量替代检定提示；界面：原初学识选择与提示；测试：tests/primalKnowledge.test.cjs。
```

要求：状态词 + 事实说明 + 界面位置 + 测试文件 +（有资源时）恢复方式。没有代码的条目写清「为何不需要代码」。

## 7. Handoff 格式（teammate → Lead）

写到 `.cache/checklist-updates/<group>.json`（UTF-8，无 BOM），字段：

```json
{
  "group": "T1",
  "updatedAt": "2026-11-13T12:40:00+08:00",
  "items": [
    { "line": 31, "from": "- [ ] 1 级 · 狂暴 — 待核查", "to": "- [ ] 1 级 · 狂暴 — 部分：…" }
  ],
  "wiring": {
    "imports": ["import { FooEditor, FooSheet } from './FooViews';"],
    "editor": ["<FooEditor draft={draft} onChange={onChange}/>"],
    "sheet": ["<FooSheet draft={draft}/>"],
    "charactersFields": ["fooActive?:boolean;"],
    "generationError": ["if(fc?.fooActive&&…)return '…';"],
    "derived": ["…"]
  },
  "tests": ["tests/foo.test.cjs"],
  "open": ["该条为何仍未完成/需要 Lead 决定的事项"]
}
```

- `line` 是当前清单文件的行号（1 起）；`from` 必须与文件中该行完全一致（Lead 合并脚本会校验，不一致会报错）。
- 同一 group 多次提交时，后续提交**只写增量**；Lead 每次合并后会重置。合并后行号不变（一对一替换）。
- 每完成一批（约 10–15 条）就写一次 handoff，不要等全部做完才写，避免丢失。

## 8. 命令与验证

```powershell
# 单个测试（最快）
node tests/<feature>.test.cjs
# 全量测试（注意：必须用 --test-isolation=none，否则 sandbox 下 spawn EPERM）
node --test --test-isolation=none
# 类型检查
node node_modules/typescript/bin/tsc --noEmit
# 构建（Lead 负责）
node node_modules/vite/bin/vite.js build
```

- 测试若出现 `MODULE_TYPELESS_PACKAGE_JSON` 警告可忽略（Node 24 加载 .ts 的正常提示）。
- Windows 文件系统偶发 `EIO` / `FS_STALE_VERSION`：重试一次；两次失败再报告，不要改用 shell 覆盖写。
